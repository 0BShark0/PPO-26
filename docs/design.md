# ЛР2. Проектирование системы

Язык реализации — Python 3.11+ (вместо C#/.NET из общей постановки). Соответствие:
`decimal` ↔ `Decimal`, `sqlite3` ↔ Microsoft.Data.Sqlite, `unittest` ↔ xUnit, веб-интерфейс на `wsgiref` ↔ Blazor.
Внешних зависимостей нет — только стандартная библиотека.

## 1. Структура (ЛР2-А1, ЛР2-А2)

**Архитектурный стиль — модульный монолит.** Всё приложение — один пакет Python `findirector`,
запускается одним процессом (`python -m findirector`), использует один файл БД SQLite и
публикуется одним файлом `findirector.pyz`. Сетевых сервисов между слоями нет: слои — это
подпакеты (пространства имён) одной кодовой базы, вызовы между ними — обычные вызовы функций.
Границы слоёв соблюдаются направлением импортов (Domain ничего не импортирует из других слоёв).

| Слой | Пакет | Ответственность | Зависит от |
| --- | --- | --- | --- |
| Domain | `findirector.domain` | Параметры, ограничения П-Б8/П-Б10, формулы П-Б1–П-Б7, П-Б9 | ничего |
| Application | `findirector.application` | Прогноз 3 месяцев (последовательность), сравнение, интерфейс `PlanRepository`, `PlanService` | Domain |
| Infrastructure | `findirector.infrastructure` | `SqlitePlanRepository` — реализация `PlanRepository` | Application, Domain |
| UI | `findirector.ui` | Веб-интерфейс и консоль: разбор ввода, вызов операций, форматирование | Application, Domain |

Сборка зависимостей — в точке запуска `findirector/__main__.py` (UI получает `PlanService`,
которому передан `SqlitePlanRepository`). Диаграммы: [components.md](diagrams/components.md),
[domain.md](diagrams/domain.md), [er.md](diagrams/er.md).

## 2. Контракты операций (ЛР2-Д3)

### Прогноз — `ForecastService.forecast(plan: Plan) -> Forecast`
- **Вход:** валидный `Plan` (id, название, начальные деньги ≥ 0, месяцы 1, 2, 3).
- **Алгоритм:** `cash = plan.opening_cash`, `receivables = 0`. Для месяца n = 1, 2, 3:
  `report = MonthCalculator.calculate(params_n, cash, receivables)`, затем
  **перенос:** `cash = report.closing_cash`, `receivables = report.closing_receivables` (П-Б5).
  Отрицательный `cash` переносится как есть, прогноз продолжается (П-Б6).
  После цикла `totals = PlanTotals.from_reports(reports)` (П-Б7).
- **Результат:** `Forecast(plan_id, plan_name, months=(MonthResult×3), totals)`; каждый `MonthResult`
  содержит номер и отчёт месяца: выручка, маржинальный доход, расходы, прибыль, поступления, C, D.
- **Ошибки:** `PlanValidationError` (список «поле — причина»), если план нарушает П-Б8/П-Б10.
- **Свойства:** без состояния — каждый вызов начинается с исходного плана (П-Ф6); вход не меняется.

### Сравнение — `ForecastService.compare(a: Plan, b: Plan) -> Comparison`
- Вход: два плана. Каждый считается независимо через `forecast`.
- Результат: `Comparison(left, right)` — итоги: прибыль, C3, D3, потребность.
- Ошибки: `PlanValidationError` любого из планов. Входные планы не меняются.

### Сохранение — `PlanService.save(plan: Plan) -> None`
- Повторная проверка плана; сохранение одной транзакцией (план + 3 месяца).
  Тот же `id` → обновление без дубликата (upsert).
- Ошибки: `PlanValidationError`; ошибка БД → `RepositoryError`, данные не меняются (откат).

### Список — `PlanService.list_plans() -> list[PlanSummary]`
- Результат: `(id, name)` всех планов, упорядочено по названию. Пустой список — не ошибка.

### Открытие — `PlanService.open_plan(plan_id: str) -> Plan`
- Результат: план с теми же значениями, что были сохранены (до копейки). Отчёт не хранится — пересчитывается.
- Ошибки: `PlanNotFoundError(plan_id)`.

### Сравнение сохранённых — `PlanService.compare_saved(id_a, id_b) -> Comparison`
- Открывает оба плана и вызывает `compare`. Ошибки: `PlanNotFoundError`.

## 3. Ручной расчёт учебного сценария, A = 50% (ЛР2-Т1)

Вход: деньги 50 000; во всех месяцах Q = 5, P = 30 000, V = 10 000, F = 70 000, A = 50.
Каждый месяц: R = 5·30 000 = 150 000; переменные = 50 000; маржинальный доход = 100 000;
E = 50 000 + 70 000 = 120 000; прибыль = 30 000; S = round(150 000·50/100) = 75 000; D = 75 000.

| Месяц | Деньги на начало | Долг на начало | Поступления = S + долг | C = начало + поступления − E | D |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 50 000 | 0 | 75 000 + 0 = 75 000 | 50 000 + 75 000 − 120 000 = **5 000** | 75 000 |
| 2 | 5 000 | 75 000 | 75 000 + 75 000 = 150 000 | 5 000 + 150 000 − 120 000 = **35 000** | 75 000 |
| 3 | 35 000 | 75 000 | 150 000 | 35 000 + 150 000 − 120 000 = **65 000** | 75 000 |

Итоги: прибыль 3·30 000 = 90 000; потребность = max(0, −min(5 000; 35 000; 65 000)) = 0; D3 = 75 000.
Совпадает с общей постановкой (5 000 / 35 000 / 65 000; задолженность 75 000; доп. деньги 0).
Автотест: `tests/test_forecast.py::test_half_payment_example`.

## 4. Обоснование решений (ЛР2-Д4)

**SRP — расчёт отделён от UI.** У формул и у интерфейса разные причины для изменения:
бухгалтерское правило меняет финансист, вид таблицы — дизайнер. Формулы лежат только в
`domain` (одно место), UI лишь разбирает строки и форматирует числа. Поэтому одни и те же формулы
используют консоль, веб-интерфейс и тесты, а тесты Domain не требуют браузера или БД.

**DIP — хранилище подключается через интерфейс.** `Application` объявляет абстракцию
`PlanRepository` (`typing.Protocol`), а `Infrastructure` её реализует. Высокоуровневая логика
(`PlanService`) не знает об SQLite; зависимость направлена от детали к абстракции.
Это позволяет тестировать `PlanService` с хранилищем в памяти, заменить SQLite на другой
способ хранения без изменения формул (требование ЛР4-А1) и собирать зависимости в одной точке запуска.
