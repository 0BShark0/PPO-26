# Пояснения к лабораторным (шпаргалка для защиты)

## Главная идея предметной области

**Прибыль ≠ деньги.** Прибыль считается по выполненным работам (выручка − расходы).
Деньги — по фактическим платежам. Если клиент платит позже, прибыль уже есть, а денег ещё нет,
поэтому расходы текущего месяца может быть нечем оплатить (кассовый разрыв).
Доля оплаты A меняет только *когда* придут деньги, но не *сколько* заработано, поэтому
прибыль при A = 0/50/100% одинакова (90 000), а деньги разные.

## ЛР1 — анализ (docs/requirements.md, docs/diagrams/use-cases.md)

- Цель, границы модели, словарь (выручка, прибыль, поступления, дебиторка, кассовый разрыв), объекты.
- 3 сценария (расчёт; сравнение; сохранение/открытие) с полями «ввод — действие — результат — отказ».
- 8 приёмочных примеров ПР1–ПР8 с **числами, посчитанными вручную**: 0%, 50%, 100%, нет продаж,
  нулевые деньги, A = 101, сравнение, сохранение с копейками.
- Таблица соответствия П-Ф1…П-Ф6 → сценарии → примеры → операции → тесты (заодно закрывает ЛР3-Д1).

## ЛР2 — проектирование (docs/design.md, docs/data.md, диаграммы components/domain/er)

- **Монолит из 4 слоёв**: Domain ← Application ← Infrastructure/UI. Domain ничего не импортирует.
- Контракты операций: прогноз, сравнение, сохранение, список, открытие (вход, результат, ошибки).
- Ручной расчёт A = 50%: 5 000 / 35 000 / 65 000 — совпадает с постановкой.
- **SRP**: формулы меняются по бухгалтерским причинам, интерфейс — по дизайнерским → разные модули.
- **DIP**: `PlanService` зависит от абстракции `PlanRepository` (Protocol), а SQLite её реализует.

## ЛР3 — прогноз (findirector/domain, findirector/application, tests/test_forecast.py, test_plan_validation.py)

- `MonthCalculator.calculate` — формулы одного месяца, `MonthReport.margin` — маржинальный доход.
- `ForecastService.forecast` — цикл из 3 итераций; после каждой переносятся **два числа**:
  деньги C и задолженность D. Минус не обнуляется, кредит не берётся.
- `PlanTotals.from_reports` — итоги П-Б7; потребность = **максимум** дефицитов, а не сумма
  (тест `test_funding_need_is_max_not_sum`: сумма 120 000, а нужно 70 000).
- Все объекты неизменяемы (`frozen=True`), поэтому повторный расчёт и сравнение не портят вход.
- Проверка ввода собирает **все** ошибки сразу, у каждой — поле и причина.

## ЛР4 — хранение (findirector/infrastructure/sqlite_repository.py, tests/test_sqlite_repository.py)

- Таблицы `plans` и `month_plans`, PK `(plan_id, month_number)` = уникальный номер месяца.
- Деньги хранятся **целым числом копеек** — копейки не теряются (тест с 1 000,01 и 333,33).
- `PRAGMA foreign_keys = ON`; сохранение — **одна транзакция** (upsert плана + перезапись 3 месяцев).
- Хранятся только входы, отчёт пересчитывается. Формулы для БД не менялись.

## ЛР5 — интерфейс (findirector/ui/web.py, docs/ui.md, tests/test_e2e.py, docs/e2e-protocol.md)

- Страницы «Планы», «План», «Сравнение». Аналог Blazor — сервер `wsgiref` из стандартной библиотеки.
- Отрицательные деньги подписаны «Не хватает денег». Ошибки подсвечивают поле.
- После правки поля старый результат скрывается (JS), пересчёт — всегда с текущих данных формы.
- Сквозной тест: 2 плана → расчёт → сохранение → сравнение → «перезапуск» → открытие →
  изменение → пересчёт → ошибочный ввод.

## П-Т1: объяснение одной формулы (пример ответа)

**Оплата текущих продаж и задолженность (П-Б3, П-Б9):** `S = round(R × A / 100, 2)`, `D = R − S`.
- Требование: П-Б3 и П-Б9 в docs/requirements.md (словарь, ПР8).
- Код: `findirector/domain/month.py`:
  `paid_now = round_money(revenue * plan.paid_now_percent / 100)` и `receivables = revenue - paid_now`.
  `round_money` использует `ROUND_HALF_UP` — это то же, что `MidpointRounding.AwayFromZero` в .NET.
- Почему D вычитанием: если округлять и S, и D отдельно, при R = 0,05 и A = 50 получилось бы
  0,03 + 0,03 = 0,06 ≠ 0,05. Вычитанием: S = 0,03, D = 0,02, в сумме ровно выручка.
- Проверка: тест `test_half_kopeck_rounds_payment_but_preserves_total_revenue` и
  `test_kopecks_example` (S = round(329,9967) = 330,00; D = 669,99).
